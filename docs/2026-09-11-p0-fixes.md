### Root causes confirmed (live-verified)

- **F1**: `teacherService.getTeacherToday` (live path) defaulted the schedule to the
  fixture `getTeacherScheduleFallback()` and only replaced it when the DB returned rows.
  Sarah has no `timetable_entries` as teacher in the published timetable, so fake entries
  (with fixture id `tt-entry-001`) reached the "Open Scheduled Lesson" CTA and the cockpit
  query for that id failed. Two aggravators: employee resolution skipped lookup for emails
  containing "teacher" and hardcoded `99999999-…-991`; a "Canonical Sarah P5 Blue" block
  fabricated a class responsibility in the live path.
- **F2**: `parentService.getChildOverview` selected `student_name, class_name, stream_name`
  from `activity_enrolments`, but the live table only has
  `id, school_id, activity_id, student_id, charge_id, status, enrolled_at`
  → PostgREST 42703 → red banner. Guardian seed data itself was fine
  (Florence → Amari verified live). Secondary UX defect: the page rendered the error banner
  AND the "No overview available" empty state simultaneously.
- **F3**: two `people` rows shared the email `student@somacampus.ug`
  (`11111111-…-0010` from `supabase/seed.sql`, `6ff0e4d3-…` created by
  `scripts/seed-auth-users.ts` running against a DB where seed.sql had not yet run /
  re-ran later). `onlineStudentService.resolveStudentId` used `.maybeSingle()` on the email
  lookup → PGRST116 raw error rendered to the learner.
- **F4**: `timetables` / `timetable_entries` have SELECT-only RLS policies
  (deny-by-default by design), but `TimetableWizard.publishAll` inserted directly into both
  tables before calling the atomic approve/publish RPCs →
  "new row violates row-level security policy for table timetables".

### Changes (final — includes two extra bugs found during GUI re-verification)

1. **`supabase/migrations/20260922000008_timetable_publish_rpc_and_people_dedupe.sql`** (PUSHED LIVE)
   - New leadership-gated `SECURITY DEFINER` RPC `create_timetable_with_entries(school, term, name, entries jsonb)`
     that validates the payload and creates the timetable (`status='reviewed'`) plus all entries
     in ONE transaction. Granted to `authenticated`. Mirrors the existing
     `approve_timetable_atomic` / `publish_timetable_atomic` pattern; RLS stays SELECT-only.
   - Deterministic people-email dedupe: keep the identity-referenced row (tie-break lowest id),
     delete unreferenced duplicates (0 refs verified for the live duplicate), detach (null
     email/auth_user_id) any referenced ones. Live result: `student@somacampus.ug` now has
     exactly 1 people row.
2. **`src/modules/planning/TimetableWizard.tsx`** — `publishAll` now calls
   `create_timetable_with_entries` instead of direct inserts into `timetables`/`timetable_entries`,
   then proceeds with the existing approve → publish RPCs. No partial week can be left behind.
3. **`src/modules/teacher/teacherService.ts`** (F1, plus D2 which shares the file)
   - Live path starts from an honest empty schedule (`[]`); fixture fallback removed.
     No fixture id can reach the cockpit URL any more; the page renders a truthful
     "no lessons scheduled" state (the page already had an empty-state branch).
   - Removed the "Canonical Sarah P5 Blue" fabricated-responsibility fallback.
   - Employee resolution rewritten: email → `people` → `employees` (fail-closed with clear
     errors). No hardcoded `99999999-…-991`, no email-contains-"teacher" special case.
     (Live check: Sarah's employee row IS `99999999-…-991`, so behaviour is preserved.)
   - `dayLabel` is now derived from the queried `date` (fixes the hardcoded
     "Tuesday, 3 September 2026") and `dailyEvents` is `[]` in live (no fabricated events).
4. **`src/modules/teacher/TeacherTodayPage.tsx`**
   - Events card renders only when events exist.
   - **EXTRA BUG (cross-user identity leak)**: the page hardcoded
     `getTeacherToday('teacher@somacampus.ug', …)` — every signed-in teacher saw Sarah's

### Follow-up: classic "Submit for Review" path (external review finding, fixed)

An external review of this pass correctly flagged that `handleSubmitForReview` in
`TimetableDraftPage.tsx` still direct-inserted into `timetables` — the same SELECT-only RLS
that blocked the wizard (pre-existing dead path, not a regression from this pass, but a
real gap left unaddressed). Fixed with two more migrations + the page change:

11. **`supabase/migrations/20260922000009_create_timetable_with_entries_meta.sql`** (PUSHED LIVE)
    - Extends `create_timetable_with_entries` with optional `p_scorecard`,
      `p_base_timetable_id`, `p_is_ai_generated` parameters. The scorecard matters: it feeds
      `approve_timetable_atomic`'s zero-hard-violations gate, so submitting through the RPC
      must carry it or approval would pass trivially.
12. **`supabase/migrations/20260922000010_create_timetable_reviewed_inactive.sql`** (PUSHED LIVE)
    - Correction found during GUI verification: a 'reviewed' submission is a draft for
      leadership and must NOT be the active timetable — activation belongs to
      `publish_timetable_atomic` (which activates the target and archives all other active
      timetables in the term). The RPC now inserts with `is_active = false` and the redundant
      4-arg overload is dropped (one canonical 7-arg signature; 4-arg callers resolve via
      defaults). Live data repaired: the reviewed copy created during verification was
      deactivated; exactly one active timetable remains.
13. **`src/modules/planning/TimetableDraftPage.tsx`** — `handleSubmitForReview` now calls the
    RPC with the solver payload + scorecard instead of direct inserts.
    (Cosmetic note: the old insert also wrote `ai_explanation`; the RPC does not carry that
    text field — the governance-relevant `constraint_scorecard` is preserved.)

Verification: typecheck green, 840/840 tests green, migration live-verified (single 7-arg
function with EXECUTE for authenticated; one active timetable). GUI: Advanced controls →
Step 2 solver → "Submit for Review" advances status PUBLISHED → REVIEWED with an
"Approve Timetable" button and no RLS error (`fix_f4b_classic_submit.png`); draft page
reloads cleanly (single-row active lookup intact); teacher Today shows exactly 1 lesson

governance view reflects the ACTIVE timetable's status after reload, so an inactive
